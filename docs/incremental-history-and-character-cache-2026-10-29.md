# 履歴の差分取得とキャラ解説の再利用

## 維持する仕様

- 対象期間60日、更新スケジュール、Pythonの集計式・時間重み・重複排除・ランク条件は維持。
- 毎回、最新のプレイヤーランクを取得して60日分を再計算。履歴だけを再利用し、計算済みの勝率を加算する方式にはしない。
- 3種類の統計テーブルは従来の `replace_analytics_snapshot` でまとめて更新。
- キャラ解説のJSON構造、全体・ガチ、マップ・モード別統計、相性・シナジー、新キャラ検出、404/503を維持。

## 対戦履歴

`analytics_history_days` は対戦日と変更トークンだけを保持する。挿入・削除・訂正・日付移動をステートメント単位のトリガーで記録する。
同一内容の再保存と、分析に使わない `collected_at` だけの変更は無視する。最後の1件が削除された日も記録を残す。
ランク変更は履歴トークンに含めず、毎回のランク取得で反映する。

集計前に小さな変更一覧を読み、変更された日の履歴だけを再取得する。日付の途中に60日の境界が来る場合は、保存済みの1日分から正確な時刻で絞り込む。
DBからの取得後にも変更一覧を確認し、取得中に変わった日は再試行。3回とも変更された場合は集計結果を公開せず終了する。
初回・キャッシュ消失・暗号鍵変更は再取得する。変更一覧のRPCを使えない場合は既存の全件取得へ戻る。

GitHub Actionsの3ワークフローでキャッシュを共有する。保存するのは、gzip後にAES-GCMで認証付き暗号化した1ファイルだけ。
既存のサーバー用 `SUPABASE_KEY` から、プロジェクトURL・列構成・形式バージョンを用途に含めたHKDFで専用鍵を導出する。
秘密鍵・平文の対戦履歴・プレイヤータグはActionsキャッシュへ保存しない。改ざん・別プロジェクト・別鍵のキャッシュは再利用しない。
キャッシュが消えても機能は動くが、再構築時には全件取得の転送量が発生する。
後段の統計処理が失敗しても、取得済み・検証済みの暗号化入力ファイルは保存して次の実行で再利用する。
プレイヤーランクの取得も主キーを基準に続きから読み、OFFSETによる読み飛ばしを避ける。抽出条件・順序・ランク判定は同じ。

DBには重い統計計算を追加せず、日単位の小さな変更記録だけを追加する。日付検索用インデックスは約6.2MiB。
変更一覧の実行時間は本番で0.964ms、直近1日189件の取得は4.017ms（一時ディスク書き出し0）。いずれも単発測定。

## キャラ解説

集計スナップショットの世代とキャラIDで完成済み応答を再利用する。上限128件、有効期限1時間。
同じキャラの同時リクエストは1回の生成を共有し、別キャラや一覧取得はその相性取得を待たない。
その前提となる共通統計も、空キャッシュ時の取得を共有する。8件同時に来てもDBからの読込は1回だけで、更新前に開始した読込が新キャッシュを上書きしない。
日次更新・明示的キャッシュクリア・集計スナップショットの世代変更で再生成する。古い処理が完了しても、クリア後のキャッシュには登録しない。
応答はコピーして返すため、別リクエストによるデータ変更を共有しない。失敗応答は保存しない。
初めて取得するキャラの相性SQLそのものを高速化した変更ではなく、異なるキャラが集中する場合のSQLタイムアウト解消は保証しない。
DBの読み取りだけは、HTTP/2切断・ReadError時に1回だけ再試行する。SQLエラー・SQLタイムアウト・書き込みは再試行しない。

## 検証

- 実際のPostgRESTクライアントと模擬HTTP応答で、ページ分割、過去の遅延到着、訂正、削除、日付変更、期間境界、取得中の変更を確認。
- 暗号化ファイルの破損・消失・鍵変更・プロジェクト違いから復旧。
- 同じ入力・同じ基準時刻で、マップ統計・対面相性・味方相性が全件取得版と一致。全ランク帯を確認。
- 履歴を再取得しない2回目の実行でも、最新ランク13→19に応じてガチのエリート帯→マスター帯の集計が更新される。
- 1,600件・20日分の模擬データでは、変更のない2回目は変更一覧2回だけで、応答本文のバイト数は初回の1%未満。月間使用量の削減率ではない。
- キャラ解説の全フィールド・非中立の相性とシナジーを比較。同じキャラへの8同時リクエストでも詳細生成は全体・ガチ各1回。
- DBでサービスロールによる挿入、変更なしの更新、訂正、日付・主キー変更、最後の行の削除を検証。テスト行と変更記録はロールバックし、残存0件。
- 新しいDB機能はanonからテーブル参照・関数実行とも不可。セキュリティ診断の新規指摘なし。
- フロントの公開統計キャッシュ、ドラフトデータ共有、ライブキャラページの検証が成功。
- 最終バックエンドテストは142件成功、既存失敗1件を除外。

本番キャラ解説・一覧・ピック支援は200。更新前後で、一覧・集計値・推薦結果は一致。
相性の35項目には、古いキャッシュから新しい生履歴の読み直しによる差があった（参照件数の増加も確認）。同一時刻の全項目一致という検証とは区別する。
同じ本番キャラ解説の連続取得は内容が完全一致し、0.125〜0.469秒。デプロイ直後の初回生成は19.375秒で、初回の遅い経路は残る。
追加のログ確認ではキャラ詳細APIにHTTP/2接続切断による503が2件あり、これを受けて上記の読み取り再試行を追加した。
初回の本番集計検証では、300,061件の対象履歴（取得300,200件、61日区画）の入力キャッシュ生成まで成功した。
その後、従来のランク取得がOFFSET 29,000でSQLタイムアウトしたため、統計公開前に安全に停止した。
ランク取得を主キーの続きから読む方式に修正し、検証済み入力キャッシュは後段失敗時も保存するよう変更した。
修正後はランク8,573人の分類と3種類の計算を完了したが、既存の一括保存RPCが8秒でタイムアウトした。
このバックグラウンド保存関数だけを30秒に設定し、トランザクションによる一括更新と既存の実行権限を維持した。画面用の相性関数・ロール・DB全体の制限は変更していない。
参照：[Supabase公式の関数単位タイムアウト設定](https://supabase.com/docs/guides/database/postgres/timeouts#function-level)。
差分取得の再試行が起きた場合、ログの取得件数は全試行の累計を記録する。

## 復旧

`ANALYTICS_HISTORY_CACHE` を指定しない実行は従来の全件取得になる。集計期間・頻度を下げて転送量を減らす変更はしていない。
キャッシュが使えない場合も、空の履歴で統計を上書きしない。
